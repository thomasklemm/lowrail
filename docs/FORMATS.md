# Data formats

All files are JSON, written under `<app>/.lowrail/`.
Facts and runtime manifests use **format 2**; the observation and other report
formats below keep their independent version numbers. App-owned metadata paths
are relative to the app root, including template identifiers and map keys.
`app_root` locates that root relative to the JSON file's directory (normally
`".."`). `app_paths.values` and `app_paths.keys` are JSON pointers identifying
exactly which metadata values/maps must be expanded by readers. The Ruby and
Rust readers resolve values before renaming parent map keys. Ruby source,
configuration, schema literals and reflection options are never text-rewritten.
External gem paths remain absolute and must still satisfy their certificates.
In-memory facts returned by `Facts.collect` remain absolute; persistence uses
this relative representation. An IO dump is anchored to the supplied app root.

## facts.json — what the booted app looks like

Written by `gem/exe/lowrail-facts` (run inside the app as
`bundle exec ruby /abs/gem/exe/lowrail-facts OUT.json`; the app's Gemfile is
never touched). It sets `RAILS_ENV=test` unless set, starts the generated
code capture, requires `config/environment`, runs the materialize steps
(below; `--no-materialize`: only `Rails.application.eager_load!`), then
dumps. `lowrail facts APP [--out PATH]` runs it with cwd APP and writes
`APP/.lowrail/facts.json` and `APP/.lowrail/generated/<sha256>.rb`. Raw observations only; classification (e.g.
"generated by `has_many`") happens in Rust (`src/facts/origin.rs`), where
Prism can look at the source span.

Methods are listed per module for the methods **owned by or visible on** that
module: public, protected and private `instance_methods(false)` on the module
and on its singleton class (`"singleton": true`), so the dump stays linear in
the app size. Resolution facts (`Article#title` → owner) for a receiver are
derived from the ancestors chain. `owner` differs from the module (or
`#<Class:Mod>` for singleton methods) when `instance_methods(false)` reports
methods of a prepended module or a ZSUPER entry (`private :inherited_method`);
61 such methods in real-blog.

`iseq_kind`: `method` (a `def`, also when it is the body of
`define_method(:x, instance_method(:y))`), `block` (`define_method` with a
block), `eval` (source path `(eval at FILE:LINE)`, i.e. string eval without a
file argument), `cfunc` (no ISeq, no source), `attr_reader` / `attr_writer`
(no ISeq but a source location), `none` (anything else without an ISeq).
Rails passes `__FILE__, __LINE__` to its `class_eval` strings, so generated
methods are mostly `method` with a source location inside the gem.

Rules the dumper follows:

- **Order of side effects.** Materialize runs before the dump. Models are
  then dumped first (a no-op after materialize, but it keeps
  `--no-materialize` dumps complete): `load_schema` and
  `define_attribute_methods` run for every concrete model whose table exists,
  so attribute methods (otherwise defined lazily on first instantiation)
  appear under `Model::GeneratedAttributeMethods`. Modules are dumped next,
  templates last (compiling them autoloads handler code the boot did not).
- **Robustness.** Every per-module, per-method, per-model, per-controller,
  per-route and per-template step rescues and appends to `errors`
  (`kind: "error"`); models without a table are `kind: "skipped"`. Core
  reflection is bound (`Module.instance_method(:name).bind_call(mod)`), so
  modules overriding `name`, `inspect`, `respond_to?`, `method`, … and
  `BasicObject` subclasses are handled.
- **Anonymous modules** are counted, not listed (except the synthetic
  ones below); so are modules whose name
  is nested in an anonymous one (`#<Class:0x…>::Config`, `anonymous_rooted`)
  and singleton classes. Anonymous modules in ancestor lists appear with
  their address stripped (`#<Module:0x>`).
- **Determinism.** Everything except `timings` is identical across runs of
  the same app: modules sorted by name, methods by (singleton, name),
  models/controllers/templates by name, gems by name, features sorted.
  Routes stay in route-set order (that order is matching semantics).
- **Synthetic modules.** Anonymous modules that hold generated methods are
  listed under descriptive names with `"synthetic": true`: the compiled
  template container (`ActionView::LookupContext.view_context_class`, or
  `…::DetailsKey.view_context_class` before Rails 8.2), the route helper
  modules (`Rails.application.routes.named_routes.path_helpers_module`,
  `…url_helpers_module`), and every anonymous ancestor of a named module,
  under the first such module by name: `Widget._enum_methods_module`,
  `Widget._store_accessors_module`, else `Widget.ancestors[3]` (e.g.
  `has_secure_password`'s `InstanceMethodsOnActivation`).
- **Templates** cover every file under `ActionController::Base.view_paths`
  that lie under the app root. `code` is what `ActionView::Template#compiled_source`
  passes through as `code = @handler.call(self, source)` (after
  `strict_locals!` and `encode!`); Lowrail can compile the same method body.

### Materialize steps

Each step calls Rails' own entry points, is guarded (failures go to
`errors` as `materialize <step>` or a narrower `where`), and reports the
delta of a census over every module (named, anonymous, singleton) of
modules, own methods, and compiled scripts. `census_boot` is the census
right after `config/environment`.

| step | what it forces |
|---|---|
| `eager_load` | `Rails.application.eager_load!` (every Rails autoloader) |
| `production_eager_load` | the rest of production's eager load: `:before_eager_load` hooks, `Zeitwerk::Loader.eager_load_all`, `Rails.eager_load!`, every `eager_load_namespaces` entry |
| `models` | per concrete model with a table: `load_schema`, `define_attribute_methods`, association `klass` and `inverse_of`, `relation_delegate_class` |
| `relation_delegation` | speculative: `generate_relation_method` for every public class method defined in app source (Rails does it on the first call through a relation) |
| `routes` | `reload_routes_unless_loaded` (lazy routes, Rails 8.0+), `finalize!`, `url_helpers`, `mounted_helpers` |
| `controllers` | `action_methods` and `view_context_class` for every controller and mailer |
| `middleware` | `Rails.application.app` (the Rack stack) |
| `i18n` | `I18n.eager_load!` |
| `templates` | every file under the controller and mailer view paths (app and engines) compiled into the real template container; non-strict-locals templates for an empty locals list (`compiled_templates`) |

### Generated scripts

`Lowrail::ScriptCapture` (`TracePoint(:script_compiled)`, installed before
`config/environment`) records every string compiled by `eval`,
`class_eval`, `module_eval`, `instance_eval` or `Binding#eval`; files are
not recorded. One entry per distinct (digest, ISeq path, ISeq first line,
receiver module, caller); `count` is the number of compilations. `path` and
`lineno` are what eval was given (`(eval at FILE:LINE)` and 1 without a
file argument): script line *k* is reported as `lineno + k - 1`. `kind` is
the eval method, `caller`/`caller_label` the code that called it, `module`
the receiver (its class for `eval`), `phase` `boot`,
`materialize:<step>` or `dump`. The source is in
`generated/<sha256>.rb` next to facts.json.

A method's `script` is set when its ISeq was compiled inside a captured
script (identity of the ISeq, through `InstructionSequence#each_child`),
including `define_method` blocks inside the script and methods whose
`source_location` points into a real gem file because eval was given
`__FILE__, __LINE__`. On VMs with fresh ISeq wrappers (4.1 preview), exact
linking is refused: `generated_stats.linking_decline` records
`iseq_identity_unavailable: ...`, and methods have no guessed `script` key.
Captured sources and ordinary method facts remain available. Bytecode/source
equality cannot replace compilation identity or certify lexical environments.
`src/facts/generated.rs` finds the exact `def` (or
call) at the relative line with Prism; untagged methods are matched by path,
line range and a `def` of that name as a fallback. `lowrail facts APP --show
Mod#meth` prints a method's origin and generated body.

## observed.json — what a test run builds and which types flow

Written by `lowrail observe APP [--samples N] [--method Mod#meth]...
[--no-types] [--facts PATH] [--overhead] [--no-run] [-- TEST COMMAND]`
(default command `bin/rails test`). The command runs with
`RUBYOPT="-I<gem>/lib -rlowrail/observe"`, `LOWRAIL=0` and
`PARALLEL_WORKERS=1` (unless set); no app file changes. Every process that
boots writes `.lowrail/observe/observed-<pid>.json` at exit; `lowrail
observe` merges them (definitions by module/singleton/name, scripts by key
with summed `count`, types with summed counts).

- **Boot** is the `after_initialize` load hook (config/environment
  loaded, before test files): the recorder snapshots every module's own
  method names there. `defined_after_boot` is every method whose name was
  not in its module at boot (`module_new`: the module itself is new).
  Anonymous modules carry the facts' synthetic names where they apply,
  else `#<Class < Super>` / `#<Module>`.
- **Types** are sampled for app methods (source under the app root, not
  `vendor/`, `tmp/`, `test/`, `spec/`), hooked at boot and as Zeitwerk loads
  app constants, plus `--method` framework methods. Each method gets its
  own `TracePoint(:call, :return)` enabled with `target:`, which
  instruments only that ISeq and disables itself after `samples_per_method`
  returns (`saturated`); cfuncs and attr methods cannot be targeted.
  Classes are the shallow `obj.class` (core reflection, never the object's
  own methods); anonymous `*`/`**`/`&` parameters are not sampled.
- **comparison** (when facts.json exists): a method counts as in the facts
  by module and name, by the same generated script digest or the same name
  and generated `def` text (CodeGenerator's shared method caches), or, for
  compiled template methods, when the facts compiled the same template
  file. The rest is grouped by where its body comes from.

## manifest.json — what the runtime gem loads

Written by `lowrail build` (via `gem/exe/lowrail-compile`).

Ordinary guarded manifests have no `tier`. `build --env production --sealed`
adds `"tier": "sealed-v1"`; the runtime requires production in both the
artifact and process, `LOWRAIL_SEALED=1`, and only registry `sealed_only` units.
Unknown/missing tiers on sealed-only units and old mixed artifacts refuse as
a whole before installing any pass. There is no test-certificate bypass.
See [the separate contract](sealed.md#artifact-acceptance-and-the-first-delivered-slice).

```json
{
  "format": 2,
  "ruby_description": "...",
  "app_root": "..", "build_root": "/build/app", "iseq_root": "/deploy/app",
  "app_paths": {"values": ["/units/0/file"], "keys": ["/files", "/templates"]},
  "relocation_refusals": [],
  "compile_option": "<sha256 of sorted RubyVM::InstructionSequence.compile_option>",
  "rails_env": "test",                                  // units apply only in this env
  "files": {"app/helpers/rooms_helper.rb": {
    "iseq": "iseq/<sha>.bin", "source_sha256": "...",
    "lowered": "src/app__helpers__rooms_helper.rb", "lowered_sha256": "...", "iseq_sha256": "...",
    "compile_option": "<sha256 of this file's compiler defaults and explicit options>",
    "portable_fingerprint": true,
    "original_iseq_sha256": "<sha256 of the app loader's original ISeq binary>"}},
  "templates": {"app/views/articles/_article.html.erb": {
    "source_sha256": "...", "code": "<lowered compiled ERB code>", "units": [0, 1]}},
  "units": [{
    "id": 1, "kind": "template", "file": "app/views/articles/_article.html.erb",
    "pass": "route/path", "sites": 3,
    "facts": [
      {"receiver": "@self", "method": "article_path", "owner": null,
       "source_location": "/abs/gems/actionpack-8.1.4/lib/action_dispatch/routing/route_set.rb:334",
       "visibility": "public",
       "route": {"name": "article", "spec": "/articles/:id(.:format)", "parts": ["id"],
                 "defaults": "{controller: \"articles\", action: \"show\"}"}},
      {"receiver": "ActionDispatch::Http::URL", "method": "path_for", "singleton": true,
       "owner": "#<Class:ActionDispatch::Http::URL>", "source_location": "/abs/...:169", "visibility": "public"}
    ]
  }]
}
```

File delivery requires all three per-file checks: unchanged source bytes,
the same compiler recipe, and the same original ISeq from the **live loader
chain**. The recipe hash uses the sorted process-default options and, when
non-nil, the explicit per-call options (sorted if a Hash). Both are recorded
at the actual compiler call, not when the loader finishes: Freezolite restores
its temporary defaults after each load. Native Bootsnap cache hits record the
selected compiler's options at `storage_to_output`; an opaque compiler whose
recipe cannot be observed is not trusted. The original ISeq fingerprint
additionally detects source transforms and bytecode hijacks. It alone would
not detect option changes that affect only newly introduced lowered code.
Registered require-hooks hijacks therefore cannot borrow the selected
Bootsnap compiler's recipe: their warm cached bytecode runs unchanged when
the actual compilation policy is no longer observable.

The top-level `compile_option` remains build-process metadata, not a file
delivery guard. Format-1 manifests now refuse as a whole with a recorded
rebuild reason; Rust can still read same-root format-1 facts. File delivery also
validates the lowered source and binary digests. `iseq_root` is the required
runtime root for a file-binary artifact; `build_root` is provenance, never a
lookup root. For `--target-root`, `portable_fingerprint` selects the full
`ISeq#to_a` Marshal digest, normalizing **only** the root `<main>`/`<compiled>`
label; operands, nested frame labels, paths and literal Strings are preserved.
The build must first reproduce the observed original under that rule. Other
serialization versions or changed nested frames refuse instead of being
normalized away. Same-root file builds retain the original binary fingerprint.
Opaque path-bound certificates are listed in `relocation_refusals` and the
`delivery/relocation` ledger; moving such a build refuses at boot.
Coverage always runs original source. See [loader composition](loaders.md)
for the gem survey, installation-order behavior, and tested versions.

Units: `kind` is `"template"` (code served through the template seam,
`file` is the template identifier) or `"file"` (a Ruby file served through
`load_iseq`); `pass` names the lowering pass (`view/link_to`, `route/path`);
`sites` counts lowered call sites. Unit ids are unique across passes.
Method/model variants retain `kind: "runtime"` and their existing pass-specific
payloads (`preload_facts`, `ar_instantiate`, `ar_plans`). They need no compiled
file. The runtime install contract is unchanged by migration steps 1–3;
the target `target`/`data` unit layout is not introduced here.

Facts: a method fact holds when `receiver#method` (or `receiver.method` with
`"singleton": true`) resolves to that owner, source location and visibility
(`owner: null` = an anonymous module, matched by source location).
`"receiver": "@self"` means the class of `self` at the call site: lowered
code calls `::Lowrail.ok?(id, self.class)` and the facts are checked per
class, cached until a hook resets the unit (`"@view"` from earlier builds is
read the same way). A fact with `"route"` additionally requires the method to
be owned by `Rails.application.routes.named_routes.path_helpers_module` and
the named route to still have that path spec, required parts and
`defaults.inspect`, with no requirements and no glob.

## build input for lowrail-compile — `units.json`

```json
{"out": "/abs/app/.lowrail", "app_root": "/abs/app", "target_root": "/deploy/app", "rails_env": "test",
 "files": [{"path": "/abs/app/models/article.rb",
            "lowered": "/abs/app/.lowrail/src/app__models__article.rb",
            "original": "/abs/app/.lowrail/src/app__models__article.rb.orig"}],
 "templates": { ...as in manifest... },
 "units": [ ...as in manifest... ]}
```

`lowrail-compile` runs under `bundle exec ruby`, boots `config/environment`
with `LOWRAIL=0` and the requested `rails_env`, and eager-loads the app while
observing compiler calls for the target files. A temporary
`BOOTSNAP_CACHE_DIR` prevents warm caches from hiding those calls and is
removed afterwards; the app's existing cache is untouched. It then compiles
each lowered source with the original path, parser, line, process defaults
and explicit options, writes binaries, and atomically writes `manifest.json`.
Defaults are restored after every compilation, including syntax errors.
Optional `target_root` comes from `lowrail build --target-root PATH`; it must
be absolute but need not exist during build. Only app-owned file compilation
filenames change; gem file paths and compiler policy do not. The runtime does
not recompile lowered files. See [the deployment contract](loaders.md#deploy-paths).
Without a Rails environment (standalone compiler fixtures), the recipe is
the current process's `compile_file` policy.

A file is skipped with a warning (and its units dropped) if the app did not
visit an observable compiler, if its loader transformed the source before
compiling (the current passes analyze disk source), or when its SHA-256 differs from
`source_sha256` or, if given instead, from the SHA-256 of the `original` copy
the pass lowered. `templates` and `rails_env` are copied to the manifest;
template units need no compiled file.

### Build orchestration and private runtime-builder protocol

`src/passes.rs` declares pass names, source/runtime kind, defaults, aliases
and builders in execution order. Source passes run over each template/file
in that order (link_to before routes). Runtime passes run in one
`bundle exec ruby gem/exe/lowrail-runtime-build` process, with the app already
booted and eager loaded. No runtime process is launched when none is selected.

Rust sends one JSON request on stdin:
`{"builders":[{"file":"preload_build","module":"PreloadBuild"}],"denied":[]}`.
The registry supplies these names, not app input. Each module's
`build(denied: [])` returns `{units:, ledger:}` without reading/writing build
artifacts. Stdout returns an array of those results in registry order; app
stdout is redirected to stderr before boot so logging cannot corrupt JSON.

Digest lowering additionally returns `files: [{path:, original:, parts:}]`.
Each part is literal source text or a numeric index into that result's units.
Rust allocates final ids and renders only those numeric parts; source strings
are never searched/replaced for ids. This preserves arbitrary Ruby literals
and UTF-8 source. Builders neither allocate global ids nor write source files.

Rust merges units/diagnostics, assigns runtime ids after the source ids,
normalizes the combined ledger, and writes `units.json` and `ledger.json`
once. The compiler observes the app's per-file loader policy in its own boot,
compiles lowered files and writes `manifest.json` once. Runtime units pass
through compilation unchanged. There are no per-pass artifact rewrites.
The compiler then atomically appends/replaces only `jit/shape` warning rows in
the ledger, after inspecting the emitted binaries; it does not rewrite pass decisions.
With cached facts, a default build has two app boots (oracle + compiler);
an all-pass build has three (plus the shared runtime builder), down from six.
A fresh facts dump adds one boot in either design.

## ledger.json — every site a pass looked at

Written by `lowrail build`, using the same schema for all passes:

```json
[{"pass": "route/path", "target": "/abs/app/views/articles/_article.html.erb", "line": 13,
  "site": "edit_article_path", "outcome": "lowered", "reason": "lowered", "detail": "lowered", "copies": 2},
 {"pass": "route/path", "target": "/abs/app/models/webhook.rb", "line": 45,
  "site": "message_path", "outcome": "refused", "reason": "overridden_helper",
  "detail": "Webhook#message_path is defined by Webhook, not the route set", "copies": 1}]
```

`target` replaces `file`/`template`/`method`: a source path, model name,
association label or, for a whole-pass diagnostic, the pass name. `site`
replaces `helper`/`method`, with `"*"` when no narrower site is known.
`line` is 0 for non-source diagnostics. Pass decisions have `outcome`
`lowered` or `refused`; `detail` preserves the complete previous free-text outcome.
The Rust build boundary normalizes both source and Ruby builder diagnostics.
Compiler-only `jit/shape` rows use `outcome: "warning"`, never lowering or
refusing a unit. Their reasons and inspection gaps are documented in the
[JIT shape guide](jit-shapes.md#cheap-build-time-check).

One entry per diagnostic site/outcome; `copies` (always present, at least 1)
preserves repeated occurrences in a pass's input. A helper copied into both
branches of a lowered link_to has two copies but one ledger row. Build's
single refusal table groups rows by `(pass, reason)` without multiplying
copies. Runtime `eligible …` and `lowered (homogeneous results only)` outcomes
now count as lowered, not refused. This describes build eligibility, not
runtime coverage; use verify hits/fallbacks to establish coverage.

Codes are stable within each pass. `detail`, not the code, carries variable
helper/model names, paths, exceptions and probe differences.

All passes may use `denylisted` (verify's bisection), `builder_error` (a
rescued build exception) or `unclassified` (a new unmapped explanation,
never discarded). Plain successful source/digest sites use `lowered`;
preload eligibility uses `runtime_tree`, AR scoped readers `scoped_reader`,
and instantiation `homogeneous_results`.

Every build now records whole-pass `quarantined` refusals for `view/link_to`
and `route/path`, including when neither was selected. Neither can be opted
in. An older manifest containing either pass is incompatible as a whole;
`Lowrail.refusal_reason` and a boot warning explain why no units or templates
were installed. See [the counterexamples](passes/endpoint.md#source-arm-quarantine).

Template source passes also use `template_context` when a handler body parses
inside Action View's method context but not at top level (for example a
layout's bare `yield`), or `template_parse` when the wrapped body still fails.
Both record a whole-handler `compiled_body` refusal and retain original code;
this diagnostic does not broaden lowering eligibility or add runtime hits.
The AR query inventory remains under `active_record/ar_plans_survey` (not
a separately selectable pass); its `receiver`, `shape` and `app` metadata
are retained. It reports unsupported source queries, never successful units.

## verify outcomes — `outcomes-<mode>.json`

Written by the Minitest or RSpec reporter (`LOWRAIL_OUTCOMES=path`), both
installed through `RUBYOPT=-rlowrail/setup`, without app/Gemfile changes:
`{"tests": {"ArticleTest#test_x": {"result": "pass|fail|error|skip", "failure": "Class: first line"}}, "unit_hits": {"0": 12}}`.

RSpec keys are `example.id` (file plus scoped example id), not descriptions,
which can be duplicated. RSpec passed/failed/pending map to pass/fail/skip;
failed expectations and unhandled exceptions both use RSpec's failed status.
Failures include the exception class and full message (expectation messages
often start with a blank line), with object addresses masked. Pending examples
include their exception or skip reason; unexpectedly passing pending examples
remain failures. Each RSpec process writes `path.<pid>`; Minitest also writes
an aggregate `path` after its forked workers finish. Verify reads the aggregate
when present, otherwise the per-process files, so hits are not counted twice.
Use `lowrail verify APP -- bundle exec rspec --seed 12345` for RSpec; custom
test commands are also accepted by `lowrail observe`.

Outcome writers include `ruby: RUBY_DESCRIPTION` (merged Minitest files use
`ruby_descriptions`). Verify preserves the distinct descriptions for each
off/on run, making the [explicit mise Ruby axis](ruby-4.1.md) auditable.
`LOWRAIL_JIT_DIAGNOSTICS=1` adds a `jit_diagnostics` array of **separate
process-lifetime snapshots**, not additive per-test or per-ISeq counters.
Unavailable values are null. Verify retains this array under
`last.json` → `report.off/on.jit_diagnostics` without including it in any gate.
See the [counter scope and limitations](jit-shapes.md#diagnostic-counters-never-gates).
