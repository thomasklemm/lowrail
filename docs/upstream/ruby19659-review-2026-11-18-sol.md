## The two shapes

The original-count requirement is real. On the candidate, `gen_invoke_block_iseq_direct` subtracts `args.len()`
from the snapshot's stack length for the saved caller SP and stack map (`codegen.rs:2150–2155`), passes that count
to `gen_push_frame` (`:2157`), and derives the new SP from the resulting stack size (`:2168`). Only then does
it slice the native call arguments and `IseqCall.argc` to `lead_num` (`:2180–2186`). `gen_push_frame` places the
environment relative to the same original count (`:3783` onward).

The interpreter computes `rsp = GET_SP() - calling->argc` **before** `vm_callee_setup_block_arg` truncates that
argc, then saves `rsp` and builds the block frame at that base (`vm_insnhelper.c:5599–5620`). Thus it too needs
both the original stack count and the accepted callee count. The candidate's layout is correct; the surplus
values need not be cleared from memory.

Keeping the codegen slice is the smallest textual change and centralizes normalization for all three direct
block construction paths. `SendDirect` and `CCallWithFrame` also use `args.len()` for stack accounting. That is
a reasonable implementation tradeoff, not nonsense or an unsafe patch.

However, those precedents do not forbid explicit stack-effect metadata. `PushInlineFrame` already carries
`num_args` (`hir.rs:1275–1284`) and its backend uses it for the same subtraction/frame push. It has no `args`
vector, so it is not literally a precedent for two competing argument counts; it is a precedent for expressing
the frame count separately from value operands. `SendDirect` also separates normalized and exit snapshots.
The HIR already owns eligibility and the known block's identity, so recording its accepted argument operands
there is natural. The extra count earns its place by separating the two meanings presently hidden in `args`.

Smallest HIR design, demonstrated in scratch:

* Add `argc: usize` to the existing `InvokeBlockIseqDirect` variant, meaning the original yield's stack count.
* At its three construction sites (`hir.rs:3390`, `:3428`, `:3461`), set `argc` from the full vector length and
  put only `args[..lead_num]` in `args`. Keep `state`, all guards and the generic fallback's arguments unchanged.
* Thread `argc` through the existing codegen dispatch/signature. Use it in `state.stack().len() - argc` and
  `gen_push_frame(asm, argc, ...)`. The SP offset and stack map already depend on the resulting stack size.
* Pass all the now-normalized `args` to the JIT entry and use their length for `IseqCall`; remove the backend
  ISEQ lookup/slice. Print the original argc in HIR and update only the affected snapshots when making a real
  candidate. No new instruction, wrapper type, generic argument planner or change to `PushInlineFrame` is needed.

Normalizing the frame snapshot instead is another possible design, using existing `with_replaced_args`, but
then overflow/other pre-call exits need the original snapshot as a separate `exit_state`, like `SendDirect`.
That is more machinery than this argc field. Simply truncating the snapshot would make re-execution of the
original `invokeblock` unsafe. The scratch argc experiment did not change any snapshot.

## Test and comment review

`test_yield_surplus_args_block_side_exit_keeps_caller_stack` warms the same block with Fixnums, then gives it a
Float. `a + 1` exits the profiled Fixnum path, and `[0, yield(x, 2)]` leaves a live caller value below the args.
The expected `[0, 2.5]` checks both the block's answer and the surrounding stack shape. The three warm calls
also get past initial direct-call stubs; the test uses the existing exits-allowed assertion appropriately.

parent codegen makes this exact test abort with `[BUG] Stack consistency error (sp: 20, bp: 19)`. Adding the
original argc repairs it without restoring full HIR operands. This pins the intended regression, not merely
an arbitrary crash-free input. Passing on unmodified master is expected: master does not directly dispatch
surplus-arg yields, so this is protection against a faulty implementation of the new optimization, not a
claim to fix a pre-existing interpreter bug.

Keep `// The Float makes the block side-exit, so the interpreter returns to the caller's saved SP.` The choice
of Float after integer warmup is essential and easy to “simplify” away; the comment explains that reason in one
line. It does not narrate change history or duplicate the expected result. The other added/adapted comments
also pass DECISIONS: calling-convention/eligibility constraints, the auto-splat exception, keeping one block ISEQ
in the proxy test, and Integer#times' implicit `yield i`. No new comment reaches Ruby API documentation.

Cold read: reject non-simple blocks; reject missing args; preserve single-arg auto-splat when lead params need
it; reject throwing blocks; otherwise build the frame using all consumed stack args and pass only accepted
params. The call-flags guard protects splat/keyword/blockarg layouts; `rb_simple_iseq_p` excludes optional/rest/
post/keyword/forwarding/block params; `argc < lead_num` preserves nil padding; `argc == 1 && lead_num > 0 &&
!ambiguous_param0` preserves coercion without excluding no-param blocks; may-throw refusal preserves the existing
nonlocal-exit boundary. Tag/ISEQ guards or the already-known inlined block prove the selected handler. No guard

introduced. Both source files were already over 1,000 lines; no threshold was crossed. Flog/RuboCop metrics do
not apply to the Rust changes. The argc option adds metadata, not another dispatch branch.
