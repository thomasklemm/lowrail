## Lead 1: connection lookup (ASC1)

`Base.connection_pool` costs about 13.9k Ir on 4.0.10 (a single micro without A/A, [pool.rb](../../bench/upstream/census13r/pool.rb) with [ir.sh](../../bench/upstream/census13r/ir.sh)): `connection_handler`
3.3k (an `IsolatedExecutionState` read and `Ractors.main?`), `current_role` 3.1k and `current_shard` 3.1k (each
reads and walks `connected_to_stack`), `connection_specification_name` and `retrieve_connection_pool`. Each part is a
few small method calls; making them cheaper one by one is the kind of change DECISIONS leaves to the JITs. The
avoidable work is calling it more often than needed.

[`pool_callers.rb`](../../bench/upstream/census13r/pool_callers.rb) on casa `GET casa case edit`: association loads
call `with_connection` twice per load, once in `AssociationReflection#association_scope_cache`
(reflection.rb:300, 25 calls) and once in `Association#find_target` (association.rb:285, 25 calls), since
`fa048105d1` (2024-05) replaced `lease_connection` with two `with_connection` blocks. **ASC1** fetches the cached
statement inside the block that runs it.

* Census (`r13asc` vs `r13m`, A/A as above): median −0.26%; blog +0.16%, casa −0.26%, react-starter-kit −0.40%,
  redprints-cfp −0.39%; max −0.91%, none beyond 1%.
* Body run ([body/ASC1](../../bench/upstream/census13r/body/ASC1)): interpreter belongs_to −3.1%, has_one −3.0%,
  has_many −2.4%, A/A ≤ 0.06%; YJIT cells not JIT-flat. Master × interpreter and ZJIT:
  [body/ASC1-master](../../bench/upstream/census13r/body/ASC1-master).
* Probe ([probe.rb](../../bench/upstream/census13r/probe.rb), [data/probe](../../bench/upstream/census13r/data/probe)):
  identical records and SQL, prepared statements on and off; one checkout fewer per load without a leased connection.
* Tests: the first run loaded main's activerecord through main's Gemfile and is void. With the branch's own Gemfile, the
  activerecord SQLite suite on 703f89d6f6 (which also updates `association_route_test.rb`, found by thermos-sol):
  10,485 runs, 0 failures, 4 errors, all `sqlite_rake_test` needing the `sqlite3` CLI, as on main.

**Dropped variant (`StatementCache#execute`):** `StatementCache#execute` calling `_query_by_sql` with the connection it already has,
instead of `find_by_sql`, which takes the connection again: −5.5% on `Post.find`, −2.3% on has_many load
(interpreter, A/A ≤ 0.07%, [data](../../bench/upstream/census13r/data/statement-cache-execute-interp.txt)). Not exact: bullet
(`find_by_sql` override in every `active_record*.rb`) and goldiloader (`QueryingPatch#find_by_sql`, with a comment
that association queries go through `find_by_sql` via `StatementCache#execute`) rely on that path.

**The eager order matcher (#59413, lead sweep input):** `preprocess_order_args` and `pluck` pass
`model.adapter_class.column_name_with_order_matcher` to `disallow_raw_sql!` eagerly, and `adapter_class` resolves the
pool. On casa `GET casa case edit` that is 53 lookups, about 0.74M of 137M Ir (0.54%); in the other three apps 0–3
per request. #59413 made it lazy with a new keyword and was closed by its author after fatkodima doubted the value and
Discourse turned out to override `disallow_raw_sql!(args, permit: nil)`. The remaining exact options are a new
keyword (breaks that override) or a Symbol/Arel check copied to each caller (the logic in the wrong layer). Held,
below the bar.

## Lead 2: query-cache key hashing (QCK1)

With #59518 merged, `QueryAttribute#hash` is memoized, and #59505 removed a third hash on a miss. What remains is
the LRU's delete and reinsert: each lookup hashes `[sql, binds]` twice. Micro (4.0.10, per call): SQL string hash
1.4k, a 2-bind `[sql, binds]` key 7.2k, one memoized bind 1.2k. **QCK1** wraps the key in an object that hashes it
once.

## Lead 3: `env_config` merge (dropped)

`Engine#build_request` merges the application's 28 `env_config` keys into each request env (18 to 25 keys). Micro
on 4.0.10: `env.dup.merge!(config)` 24.7k Ir, of which the dup is 2.7k; the same on master. The census sampler
charges 17k–112k self Ir to `build_request` for the same merge, so its 3.69% on blog `GET article.json` includes
GC and sampling attribution; the floor is about 20k Ir, 0.2–0.4% of the light workloads and under 0.1% in casa.
Middleware and apps read these keys from `env`, so skipping or deferring the merge changes what they see; a
presized hash was slower (34k). Dropped; the merge cost itself is a Ruby `Hash#merge!` matter.

## Strict Accept header (lead sweep input)

Rails 8.2's defaults set `action_dispatch.strict_accept_header = true` (`5d54357366`, 2026-06), so a browser's
Accept header is parsed instead of short-circuiting to HTML. [`accept_share.rb`](../../bench/upstream/census13r/accept_share.rb)
measures a whole blog request with Chrome's header (Callgrind, N = 20 minus N = 0, fixed heap, GC off in the
window): `GET article` 8,786,739 / 8,782,920 Ir with strict off (A/A 0.04%) and 9,106,024 with strict on, +3.6%.
`Mime::Type.parse` alone is 219k Ir for Chrome's header and 97k for Firefox's; the rest is formats-dependent work
after it.

Where the 219k go (micros on 4.0.10): `scan` 40k, the per-item `split` 31k, lookups 44k (37k of them the five types
Rails doesn't register, each built with `MIME_REGEXP` validation and then dropped by `formats`), `uniq!` on
`Mime::Type`s 22k, `AcceptItem`s and the sort the rest. It clears the bar for new apps; a simpler parse that keeps
`Mime::Type.parse`'s output is not built in this round.

### Must-fix findings and smallest fixes

1. **Correctness, medium: preserve composite equality, not explicit public sends.** In
   `activerecord/lib/active_record/connection_adapters/abstract/query_cache.rb:63–65`, `sql.eql?` and `binds.eql?`
   are not equivalent to Array's C field comparison. Pass `PrivateEqualityArray[11]` as the third argument to
   `connection.select_all("SELECT CAST(? AS INTEGER)", nil, binds)` (PostgreSQL: `$1`), where the Array subclass
   makes `eql?` private and delegates to `super`. With the cache enabled, two calls return `11` and the second
   hits on main; head raises `NoMethodError: private method 'eql?' called` on the second call. Singleton-private
   bind-array equality and private equality on a SQL String subclass fail the same way. Reusing one bind array
   whose singleton `eql?` returns false also hits on main but executes twice and stores two entries on head:
   Array's identity shortcut was lost. Reproduced on SQLite and PostgreSQL, prepared statements on/off, and
   interpreter/YJIT. This is an override of a public core method on an argument, not the accepted private Rails
   override boundary. **Smallest clean fix:** use built-in composite equality, e.g. a Struct-backed key with SQL,
   binds and the cached hash, rather than expanding the manual equality into identity/visibility special cases.
   Add one focused behavioural regression test through queries. The in-process Struct experiment below fixes
   these observed cases; a changed Rails head still needs review. No ordinary wrong-row result or security exploit
   was demonstrated.
2. **Comment gate:** delete the added line 53, `# Each lookup hashes its key twice, and hashing the binds is costly.`
   It narrates performance and the old implementation rather than preventing a reader from misreading an invariant;
   DECISIONS explicitly makes this a changes verdict. The edited pre-existing Store class comment at lines 42–44 is
   accurate representation documentation and may stay.
3. **Claims:** narrow “Each lookup hashes its key twice” in the commit message and “twice per query” in the body and
   impact. Async misses only delete/lookup and do not reinsert, so main hashes their composite once; they get overhead,
   not a saved second hash. Say “hits and synchronous misses” instead. “Equality is unchanged” is false on this head;
   fix finding 1 before retaining it. Smallest text fix is cutting/narrowing these clauses, not adding caveats or
   differential-process detail to the upstream body. In the internal note, relabel the original `find_by_sql` case
   as interpolation and Switchman's async miss as pre-existing; the executed cases below support those corrections.

The **empty-cache async miss with short SQL is the worst measured case**, not the distinct synchronous keys. It
saves no second composite hash and adds wrapper construction. Keep the cost visible; this instruction delta alone
is not the DECISIONS wall-time-loss blocker. The no-bind control is within its 0.55% A/A. No timing conclusion is
drawn from suite duration or benchmark worker elapsed times.

The new class retains SQL and binds, precomputes their composite hash, then manually checks key type and both
fields on equality; each key-construction branch otherwise remains where it was. That cold read is simple, but
the manual equality is the wrong abstraction boundary. **L2 as written** (new helper and bespoke equality); native
composite equality removes that responsibility instead of adding visibility/identity guards. No size/extraction
problem: the file grows from 344 to 359 lines. Flog total 189.4 → 204.9, cache_sql 12.4 → 13.4, lookup_sql_cache
8.8 → 9.8, new initialize 3.5/eql? 10.1: the increase comes from construction and the manual predicate. RuboCop
Metrics has the same six pre-existing offenses, none new. No need to refactor other Store logic.

Tested a Struct-backed `(sql, binds, hash)` key in memory: built-in C field equality fixes all observed argument
equality differences, keeps 38/52 objects for find hit/miss, and removes the custom predicate/readers. Main → variant:
find hit 245,030 → 237,138 Ir (−3.2%, A/A 0.01%); miss 321,463 → 313,523 (−2.5%, A/A 0.004%). It keeps most of the
gain with fewer moving parts. An Array subclass memoizing `super` also matches the full probe (including the
unprefixed override), but costs one extra allocated object per lookup for hidden ivar storage, so is not the same
allocation effect. These experiments guide finding 1's smallest fix; neither is a separately reviewed final patch.
