# Migrate background jobs from Resque to Solid Queue

## Summary

Replace Resque and resque-pool with Solid Queue. Resque payloads are not copied: operators must drain the old queues before deploying. Solid Queue uses its own SQLite database at `storage/db/production_queue.sqlite3`; normal `db:prepare` prepares it before services start.

- One worker process with three threads by default, matching the Solid Queue installer. Campfire's jobs mostly wait on HTTP (webhooks, Web Push) or the database, so threads overlap them; `JOB_CONCURRENCY` still adds processes. The queue DB pool is sized to 5 for those threads plus the poller and heartbeat, independently of web `RAILS_MAX_THREADS`.
- Queue storage retains SQLite's normal WAL auto-checkpointing. The app checkpoint contender is stopped before Solid Queue forks children and restarted by each worker/dispatcher/scheduler child.
- The performance-load environment has its own queue DB using the same schema and pool sizing.
- Posting a message writes its jobs (push, unread fanout, bot webhooks) to the queue DB in one transaction instead of one each.
- `SolidQueue.shutdown_timeout` is 8 s, so a running job gets most of Docker's 10 s stop window.
- Redis remains required for Action Cable and Rails cache until their separate migrations.

## Self-hosted cutover and backups

The [upgrade guide](https://github.com/thomasklemm/once-campfire/blob/feat/solid-queue-cutover/docs/upgrades/solid-queue.md) describes draining Resque before switching backends.

Queued jobs are treated as disposable, like cache entries. Backups snapshot only the primary database online, exactly as today; the pre-backup hook and `script/admin/prepare-backup` are unchanged from main. The self-hosting archive command excludes the queue database, and the restore hook deletes any queue database left in the volume so `db:prepare` starts an empty queue. Jobs pending at backup time (push notifications, webhooks) are not replayed after a restore, where they would be stale anyway.

## Measurements by @namespaceMarcello

[Posting load](https://github.com/basecamp/once-campfire/pull/346#issuecomment-6114638577), 16 clients posting to one room on 4 CPUs, against Resque on the base:

| Job layout | Posts/s vs base | Jobs |
| --- | ---: | --- |
| default, 1 process × 3 threads | −9% (ranges touch) | fall behind at ~285 jobs/s; 45% done when the 8 s window ends |
| `JOB_CONCURRENCY=2` | −29% | nearly keep up |
| `JOB_CONCURRENCY=3` | −35% | keep up |

Enqueueing the two jobs per post took 6.7 ms instead of 1.9 ms with the default layout, 3.6 ms of it inside the queue database's write transaction (one instrumented run).

[Interrupted room deletion](https://github.com/basecamp/once-campfire/pull/346#issuecomment-6387970909): queued jobs, such as the file purges, now survive `docker kill`, `docker stop` and an ONCE update; with Resque they went away with the container's Redis. The job running at that moment is marked failed (`ProcessExitError`, or `ProcessPrunedError` about 5 minutes after the restart) and has to be retried by hand. Nothing in this PR retries it; a targeted retry for jobs that are safe to run twice will follow as a separate PR.

[Follow-up](https://github.com/basecamp/once-campfire/pull/346#issuecomment-6418720495) on this head, 9 interleaved rounds: batching the per-post enqueues gives 239 posts/s (219–259) against 206 (191–216) before, with an A/A copy at 208 (186–218). With `docker stop` late in a room deletion, the job now finishes (2/2) instead of failing.
