# Replace Resque with Solid Queue

Jobs move from Resque in the container's nonpersistent Redis to Solid Queue in its own SQLite database, so queued work, such as a room deletion's file purges, survives a restart or update. Jobs still in Resque at the upgrade are lost, as on any restart today.

Backups copy the queue before the primary and restore both. Work enqueued between those copies can be missing after a restore; jobs running at the copy can return failed and need retrying. The worker runs three threads in one process with its own pool of five connections.
