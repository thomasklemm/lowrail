## Design

Keep the observer-validated per-worker response/authorization hot path; make presentation reuse Rails-native where its dependencies are safe.

- Replace custom FIFO bookkeeping with one approximately 64 MiB Rails `MemoryStore` for completed HTML/gzip responses and independent authorization snapshots. Retain admission limits, auth/access checks, cold-render collapse and SQLite `data_version` checks before/after reads and on admission. `CAMPFIRE_RESPONSE_CACHE_MB=0` disables this local cache.
- Use native collection caching and `Rails.cache.fetch` for viewer-independent HTML fragments, backed by #345's shared Solid Cache. Content-derived keys cover actual body, room, creator and boost/booster presentation inputs, including SQL edits without timestamp changes.
- Namespace presentation by immutable deployment revision, signing key, URL origin, mount prefix and locale. Unversioned builds get a boot-local namespace; use an immutable `GIT_REVISION` to share across workers.
- Render message pages in consecutive runs. Attachment, mention and direct-room messages render fresh, while their neighbours keep content-keyed collection hits; previously one such message disabled caching for the whole page. The views iterate `message_runs` and render each run themselves, and the action controls cache through the `cache_message_actions` block helper. This keeps the page compilable ahead of time through Roundhouse, which lowers collection renders only in templates and drops statement-form `cache_if` blocks. Detached and primary-transaction renders bypass shared fragments. Remove duplicate full-message caching, the private fragment store and Jbuilder private-method overrides. JSON renders fresh; direct sidebars preload participants rather than cache incomplete membership dependencies.
- Keep cold renders cheap: each message's cacheability is decided once per page, and a `fragment_cached` partial local tells the nested partials whether their message is already collection-cached. Collection-cached messages do not also write their text presentation and controls as separate Solid Cache entries; those nested fragments remain only for messages rendered fresh, such as in direct rooms or with mentions.
- Correct the existing cold benchmark to clear all actual stores.

## Measurements against the parent

Sequential ABBA·ABBA, eight independent processes (four per revision), Ruby 4.0.7 + YJIT, production environment with actual Solid Cache (Redis only for Action Cable on the parent), fresh database per process with 20 users, 80 deterministic messages (boosts on every seventh) and 16 authenticated sessions. 200-request warmup per workload on one session; 30 timed samples per run (15 for previously unwarmed sessions). Values average each run's p50.

| Workload | Parent | This PR | Change |
| --- | ---: | ---: | ---: |
| Room, previously unwarmed session | 98.48 ms | 44.73 ms | -55% |
| 40-message page, previously unwarmed session | 84.19 ms | 28.45 ms | -66% |
| 80-message search, previously unwarmed session | 159.67 ms | 46.23 ms | -71% |
| Room, unrelated commit before each read | 35.98 ms | 36.38 ms | +1% |
| Message page, unrelated commit before each read | 24.55 ms | 25.80 ms | +5% |
| Search, unrelated commit before each read | 49.46 ms | 48.06 ms | -3% |
| Room, fully cold caches | 162.85 ms | 151.68 ms | -7% |
| Message page, fully cold caches | 161.61 ms | 144.68 ms | -10% |
| Search, fully cold caches | 310.12 ms | 290.51 ms | -6% |

Warm whole-response hits stay around 1.8–2.2 ms in both versions, within run-to-run noise. **No universal speedup claim.** Shared fragments remove duplicate per-viewer rendering. With an unrelated commit before each read both versions are within noise. Fully cold renders were 35–40% slower than the parent on the previous head (`e67f1a8`) and are now 6–10% faster: profiling showed rich-text serialization repeated per message plus about 80 nested Solid Cache reads and inserts per cold page. Every revision's cold room p50 fell in a narrow band (parent 158.8–166.2 ms, this PR 149.0–157.6 ms). JSON throughput has not been benchmarked. These are single-process integration timings; concurrent multi-worker load is below.

### Pages with mentions or attachments

The fixture data above contains no mentions, so it does not show that a single mention or attachment previously turned off the collection cache for a whole page. Local production-mode probe with Solid Cache, 60 requests with an unrelated commit before each read, p50 over two runs:

| --- | ---: | ---: | ---: |

| Search matching those messages | 257 ms | 129 ms | -50% |
| Room without mentions | 50 ms | 49 ms | unchanged |
