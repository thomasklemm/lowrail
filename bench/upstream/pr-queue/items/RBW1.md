# Add a blog benchmark that writes

The Rails benchmarks here mostly read. In their timed iterations none of them submits a form, fails a validation, or runs after-commit callbacks, while real apps spend much of their time saving records.

This adds `blog`, Sam Ruby's [create-blog](https://github.com/roundhouse-rb/roundhouse/blob/aa60799f53b36084c6311ffcda8f14e746eebf79/scripts/create-blog) (MIT): a `rails new --css tailwind` app on Rails 8.1.4.1 with Article and Comment scaffolds, validations and Turbo broadcasts, on the default SQLite, Solid Cache, Queue and Cable stack with no external services. Each iteration makes about 420 in-process requests: reads, creates, updates, deletes, comments and a create that fails with 422, with real CSRF tokens and every response checked. Each iteration runs in one transaction per database that is rolled back at the end, as in Rails tests, with a fixed clock.

It catches changes the other Rails benchmarks never run. A small busy loop injected into `save` and `destroy` adds 2.3% to blog's instructions per iteration, and that code doesn't run at all in railsbench's or lobsters' timed iterations. Its per-request split also shows where a Rails change lands: from Rails 8.1.4.1 to main, reads take about a tenth fewer instructions while creates and updates don't get faster. Per-query and database-driver changes moved it no more than railsbench and lobsters, and about two thirds of its total is reads much like railsbench's.

Would a write workload like this be welcome? Happy to reshape it.

### Details

- **Rollback.** `benchmark.rb` pins each database's connection and opens a non-joinable transaction. Rails 8.1 opens it in `pin_connection!`; Rails main no longer does, so the benchmark opens it itself when none is open. Saves run as savepoints, and commit callbacks run when each savepoint is released, as in Rails tests.
- **Left out.** Nothing commits, so a real COMMIT and its WAL write aren't measured. Solid Cable inserts each broadcast in the request rather than on its batching writer thread. Solid Queue jobs are enqueued but never run.
- **The generated app** drops the files only deployment, development and tests use. The README lists every change; the built Tailwind CSS is checked in, so nothing is built at setup.
- **Cost.** On Ruby master an iteration takes about 1.6 s in the interpreter, 0.7 s with YJIT and 1.0 s with ZJIT. Allocations per iteration vary by less than 0.1% after two warmups, with no growth over 25 iterations.
