# Fix Rails/SelectMap false positives across record materialization

`Rails/SelectMap` currently corrects:

```ruby
query.select(:id).first(limit).map(&:id)
# => query.first(limit).pluck(:id)
```

`first(limit)` has already loaded an Array of model instances. The replacement calls Enumerable's `pluck`, not Active Record's SQL-level `pluck`: it still instantiates the models, but now fetches every column.

For `query = LintUser.order(:id)` and `limit = 3`, both expressions return `[1, 2, 3]`. The executed SQL changes from:

```sql
SELECT "lint_users"."id" FROM "lint_users" ORDER BY "lint_users"."id" ASC LIMIT ?
```

to:

```sql
SELECT "lint_users".* FROM "lint_users" ORDER BY "lint_users"."id" ASC LIMIT ?
```

Stop matching when a standard record-loading call occurs between `select` and `map`/`collect`. Relation-only chains remain eligible. This deliberately leaves `first` intact rather than changing it to `limit`, which can change implicit ordering and replace an existing smaller limit.

With five rows and ten additional string columns, the autocorrected expression allocates 134 objects per call against 106 for the original.

<details>
<summary>Standalone SQL and allocation reproduction</summary>

```ruby
require 'active_record'
require 'sqlite3'
require 'json'

ActiveRecord::Base.establish_connection(adapter: 'sqlite3', database: ':memory:')
ActiveRecord::Schema.define do
  suppress_messages do
    create_table(:lint_users) do |table|
      10.times { |i| table.string "field_#{i}" }
    end
  end
end

class LintUser < ActiveRecord::Base
end

5.times do |i|
  LintUser.create!((0...10).to_h { |j| ["field_#{j}", "value-#{i}-#{j}"] })
end

query = LintUser.order(:id)
before = -> { query.select(:id).first(3).map(&:id) }
after = -> { query.first(3).pluck(:id) }
sql = []
subscriber = ActiveSupport::Notifications.subscribe('sql.active_record') do |*args|
  payload = args.last
  sql << payload[:sql] if payload[:sql].start_with?('SELECT')
end
raise 'wrong baseline result' unless before.call == [1, 2, 3]
raise 'wrong corrected result' unless after.call == [1, 2, 3]
ActiveSupport::Notifications.unsubscribe(subscriber)

100.times { before.call; after.call }
objects = [before, before, after].map do |call|
  GC.start
  start = GC.stat(:total_allocated_objects)
  200.times { call.call }
  (GC.stat(:total_allocated_objects) - start) / 200.0
end

# With explicit order and no existing limit, these are the relations first(3)
# executes. The independently captured statements above confirm the SQL shape.
puts JSON.pretty_generate(
  before_to_sql: query.select(:id).limit(3).to_sql,
  after_to_sql: query.limit(3).to_sql,
  executed_sql: sql,
  baseline_a_objects: objects[0],
  baseline_b_objects: objects[1],
  corrected_objects: objects[2]
)
```

</details>

The regression specs cover materializing and batch-loading methods, safe navigation, parentheses, and a loading call inside a scope argument that must not prevent correction.
