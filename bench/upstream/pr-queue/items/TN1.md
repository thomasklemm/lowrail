# [Bug #21301] Normalize month-mday in Time.new before every zone path

`Time.new` mishandles a day past the end of a month with a UTC offset, a timezone object or no zone, not only with `"UTC"` ([Bug #21301](https://bugs.ruby-lang.org/issues/21301)). With day 31 and a negative offset that moves the time to the next day in UTC, the result is a month early, and a timezone object keeps the day as given:

```ruby
Time.new(2026, 2, 31, 23, 0, 0, "-05:00") #=> 2026-01-30 23:00:00 -0500, expected 2026-03-03 23:00:00 -0500
Time.new(2026, 4, 31, 2, 0, 0, TZInfo::Timezone.get("Australia/Sydney")).day #=> 31, expected 1
```

The first commit is khasinski's from #16469, unchanged. It calls `vtm_normalize_month_mday()` only in the `"UTC"` branch of `time_init_vtm()`. The second commit moves that call to right after `validate_vtm()`, ahead of every zone path. Without a zone, `Time.new` now agrees with `Time.local` for such days, which it didn't near DST changes. Days within the month behave as before. If you'd rather land this through #16469, the second commit applies on top of it unchanged.
