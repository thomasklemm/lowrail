# [Bug #21301] Normalize month-mday in Time.new before every zone path

`Time.new` misplaces day 31 of a shorter month when a negative UTC offset moves it to the next day in UTC, and with a timezone object it keeps the day as given ([Bug #21301](https://bugs.ruby-lang.org/issues/21301)):

```ruby
Time.new(2026, 2, 31, 23, 0, 0, "-05:00") #=> 2026-01-30 23:00:00 -0500, expected 2026-03-03 23:00:00 -0500
Time.new(2026, 4, 31, 2, 0, 0, TZInfo::Timezone.get("Australia/Sydney")).day #=> 31, expected 1
```

This builds on #16469, whose commit is kept as the first one. Its `vtm_normalize_month_mday()` runs only in the `"UTC"` branch of `time_init_vtm()`. The second commit calls it right after `validate_vtm()` instead, so the offset, timezone object and local paths start from a valid date too. Without a zone, `Time.new` now agrees with `Time.local` for such days, which it didn't near DST changes. Days within the month behave as before.
