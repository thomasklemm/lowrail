# Hash query cache keys with binds once per lookup

While profiling a few Rails apps, query cache lookups showed up hashing their key twice. The store keeps entries in insertion order for its LRU eviction, so a hit deletes its key and inserts it again, and a miss deletes the key before inserting the result. For a query with binds the key is `[sql, binds]`, so the SQL string and every bind are hashed twice on each hit and each synchronous miss.

This makes the key a small Struct of the SQL, the binds and their hash, computed once. Equality is unchanged: Struct compares its members with `eql?`, as the array did.

Callgrind instructions per query with the query cache enabled, Ruby 4.0.10, no JIT, objects unchanged:

| | main | this change |
|---|---:|---:|
| `Post.find(id)`, hit | 244,646 | 236,628 |
| `Post.find(id)`, miss | 321,528 | 313,180 |
| `where` with 3 binds, hit | 540,763 | 530,792 |
| `where` with 3 binds, miss | 604,020 | 593,785 |
| `where(id: ids)`, 20 ids, hit | 1,313,922 | 1,196,484 |
| `where(id: ids)`, 20 ids, miss | 1,581,836 | 1,458,428 |

Timed as thread CPU time per query over 30 rounds, these take 4.4% to 16.6% less with YJIT on Ruby 4.0.10 and 4.1% to 19.6% less with ZJIT on Ruby master, the most for the 20-id lookups. Larger IN lists save more.
