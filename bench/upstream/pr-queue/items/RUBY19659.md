# ZJIT: Drop surplus args when yielding to simple ISEQ blocks

Resolves https://github.com/Shopify/ruby/issues/1094

ZJIT now calls a simple ISEQ block directly when it gets more positional arguments than it declares, and drops the extra ones. Non-lambda blocks do this in the interpreter (`vm_callee_setup_block_arg`), and YJIT does the same. Until now ZJIT called a block directly only when the counts matched (`argc == lead_num`), so `n.times { }`, `each { }` and `yield a, b` into `{ |a| }` used the generic `invokeblock` path. The extra arguments are still evaluated, and a side exit before the call keeps all of them.

Two cases stay on `invokeblock`: a single argument passed to `|a, b|` or `|a,|`, which may be auto-splatted, and too few arguments, which are padded with nil (YJIT also leaves these out). A single argument passed to a block without parameters can't be auto-splatted, so that call is now direct. Lambdas are unaffected, because `&lambda` passes a Proc block handler.

Earlier measurements on a release build: an iteration of `200_000.times { }` took 4.6 ns instead of 25.2 ns, and the control, `{ |i| }`, took 4.6 ns before and after. They found no measurable run-time change on the 16 ruby-bench headline benchmarks.

### tekknolagi: „Warum in codegen statt HIR?“ (2026-11-18)

Er fragt zum Codegen-Hunk in `gen_invoke_block_iseq_direct`, warum die überzähligen Argumente dort und nicht in HIR
wegfallen. Ausprobiert auf ruby master `7db0202722` mit dem PR darauf: `InvokeBlockIseqDirect` in HIR nur mit den ersten
`lead_num` Argumenten gebaut, codegen.rs wieder wie auf master. Ergebnis: Absturz. Codegen berechnet den SP des
Aufrufers, die Stack-Map und den Frame-Anfang des Blocks aus `args.len()`, wie bei allen anderen Send-Instruktionen.
Der Interpreter (`vm_invoke_iseq_block_with_cref`) setzt den SP des Aufrufers unter *alle* Argumente
(`rsp = GET_SP() - calling->argc; SET_SP(rsp)`) und legt den Block-Frame über die überzähligen Plätze. Mit
gekürzter Liste stand der SP um die Zahl der überzähligen Argumente zu hoch. Sobald der Block per Side Exit im
Interpreter weiterlief und zurückkehrte, kam `[BUG] Stack consistency error (sp: 20, bp: 19)`; auch der bestehende
Test `test_getblockparamproxy_polymorphic_none_and_iseq` brach mit SIGABRT ab. Mit dem Slice in codegen (PR-Kopf)
laufen beide Tests durch.

In HIR ginge es nur mit einer zweiten Zahl an der Instruktion (Argumente auf dem Stack neben den an den Block
übergebenen). Codegen müsste dann trotzdem beide Zahlen kennen, und `InvokeBlockIseqDirect` verlöre die Regel, dass
`args` die Werte auf dem Stack sind. Deshalb nicht umgebaut, nichts gepusht, nichts gepostet; Kopf bleibt `2ec80c1bf2`.

In einem Satz: Der Aufrufer muss alle Argumente vom Stack nehmen, auch die, die der Block nicht will; das weiß nur
die Stelle, die den Frame baut, und die sieht in HIR bisher genau die Werte auf dem Stack.

**Faktencheck der Antwort auf `260bb321fe`.** `vm_invoke_iseq_block` ruft `vm_invoke_iseq_block_with_cref`, das
`rsp = GET_SP() - calling->argc`, `SET_SP(rsp)` setzt und den Block-Frame ab `rsp` baut (Locals über den überzähligen
Plätzen). `gen_invoke_block_iseq_direct` rechnet `stack_size = state.stack().len() - args.len()` und
`gen_push_frame(asm, args.len(), …)` mit der vollen Liste und schneidet erst danach auf `lead_num`, also legt es den
Frame genauso. Gleiche Rechnung aus `args.len()`: `gen_send_iseq_direct` (`SendDirect`) und `gen_ccall_with_frame`
(`CCallWithFrame`). Deshalb nennt die Antwort diese beiden statt „die anderen Send-Instruktionen“: `PushInlineFrame`
trägt seine Zahl als eigenes Feld `num_args`. Das ist auch das Gegenargument, das ein Reviewer bringen kann: ein
argc-Feld an `InvokeBlockIseqDirect` hätte ein Vorbild.

**Antwortentwurf** (nicht gepostet):

> Codegen also needs the number of args the `yield` pushed. Like `vm_invoke_iseq_block`, it sets the caller's SP
> below all of them and pushes the block frame over the surplus slots, and it takes that count from `args.len()`, as
> `SendDirect` and `CCallWithFrame` do. Dropping the args in HIR left the caller's SP too high by the surplus, and a
> block that side-exits then hit `[BUG] Stack consistency error`. Doing it in HIR would need a separate argc on
> `InvokeBlockIseqDirect`, so `args` stays the values on the stack and the call slices them. I added a test for that
> case.

Der Test auf `260bb321fe`:

```rust
#[test]
fn test_yield_surplus_args_block_side_exit_keeps_caller_stack() {
    // The Float makes the block side-exit, so the interpreter returns to the caller's saved SP.
    set_call_threshold(2);
    eval("
        def foo(x) = [0, yield(x, 2)]
        def test(x) = foo(x) { |a| a + 1 }
        test(1); test(1); test(1)
    ");
    assert_snapshot!(assert_compiles_allowing_exits("test(1.5)"), @"[0, 2.5]");
}
```
