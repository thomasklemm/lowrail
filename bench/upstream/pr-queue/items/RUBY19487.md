# YJIT: Compile super calls on Class and Module receivers

YJIT doesn't specialize `super` when the receiver has a singleton class, so that compiled code doesn't keep the receiver alive; such calls fall back to VM dispatch. That also rules out every `super` from a class method:

```ruby
class Base; def self.build = :base; end
class Child < Base; def self.build = super; end
```

This PR compiles `invokesuper` in method ISEQs when the receiver is a Class or Module. As with ordinary sends, it accepts that method-entry references may keep a singleton class and its attached Class or Module alive, since these receivers are often already referenced from constants. Other receivers with singleton classes still use VM dispatch, and the guard on the current method entry is kept, as are the assumptions that method lookup stays stable for the current method and for the method `super` calls. `super` inside a block also keeps VM dispatch, because the block can be rebound to an unrelated class.

On ruby-bench, the headline benchmarks show no measurable overall change:

| benchmark | base (ms) | PR (ms) | PR/base [min–max] |
|---|---:|---:|---:|
| headline geomean | | | 0.990 [0.970–1.009] |
| railsbench | 1497.1 | 1447.4 | 0.967 [0.895–1.015] |
| lobsters | 749.4 | 730.6 | 0.975 [0.898–1.028] |
| shipit | 1017.9 | 1013.6 | 0.996 [0.983–1.018] |
| `super` on a class (loop) | 32.6 | 8.2 | 0.251 [0.247–0.254] |
| `super` on a module (loop) | 63.8 | 11.6 | 0.182 [0.176–0.187] |

In a separate `--yjit-stats` run, `super` calls that fell back because the receiver has a singleton class (`invokesuper_singleton_class`) go, per iteration, from 77,273 to 25,961 on railsbench, from 43,256 to 4,277 on lobsters and from 33,835 to 5,114 on shipit. `invalidation_count` and `code_gc_count` don't change during the measured iterations.
