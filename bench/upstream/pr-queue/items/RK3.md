# Decode and escape form components with cgi/escape

`Rack::Utils.unescape` and `Rack::QueryParser#unescape` decode the keys and values of query strings and form bodies and every cookie value, and `Rack::Utils.escape` escapes every `Set-Cookie` value. They call `URI.decode_www_form_component` and `URI.encode_www_form_component`, which copy the string and run a `gsub` with a Hash lookup for each escape. `cgi/escape` decodes and escapes the same way, in C on MRI. It ships with every Ruby Rack supports (currently Ruby ≥2.7.3): MRI's C extension has had `CGI.escape` and `CGI.unescape(str, encoding)` since 2.4; cgi became a default gem in 2.7, and Ruby 4 retains `cgi/escape` in the standard library. Rack already requires it for `escape_html` on Ruby before 3.2. TruffleRuby uses its Ruby implementation and JRuby its own Java one.

The first commit decodes with `CGI.unescape`. It keeps URI's check for an invalid %-encoding and its message, so `InvalidParameterError` is raised as before, and like URI it decodes to bytes and converts the encoding argument once, afterwards. The second commit escapes with `CGI.escape`, which escapes `*` and leaves `~` alone where URI does the opposite, so the two are mapped back; `%2A` in its output can only come from a `*`, since a `%` becomes `%25`. Anything that isn't a plain String, String subclasses included, still goes through URI, and so does a string in an encoding that isn't ASCII-compatible, such as UTF-16: on MRI before 4.0 the C `CGI.escape` hands those to a Ruby fallback that only `cgi/util` defines. One thing changes: a `BasicObject`, which has no `instance_of?`, now raises `NoMethodError` instead of being converted with `to_s` or `to_str`.

```ruby
require "rack/utils"

rng = Random.new(7)
# A synthetic encrypted Rails session cookie: random data, IV and auth tag, Base64-encoded and joined with "--" (284 bytes).
cookie = [180, 12, 16].map { |n| [rng.bytes(n)].pack("m0") }.join("--")
token = [rng.bytes(64)].pack("m0")
form = "_method=patch&authenticity_token=#{Rack::Utils.escape(token)}" \
  "&article%5Btitle%5D=Hello+world&article%5Bbody%5D=Rack+decodes+every+form+value.&commit=Update+Article"
header = "_blog_session=#{Rack::Utils.escape(cookie)}; theme=dark"

Rack::Utils.parse_nested_query(form)
Rack::Utils.parse_cookies_header(header)
Rack::Utils.set_cookie_header("_blog_session", {value: cookie, path: "/", httponly: true, same_site: :lax})
```

Instructions are interpreter Callgrind counts per call; two runs of main differ by less than 0.25%. The figures in this description were measured on an earlier revision of this branch whose methods differ from these only in the guard line.

Both methods were compared with URI on 300,000 random strings each: escapes, lone and broken `%`, `+`, multibyte and invalid bytes, UTF-8, binary, US-ASCII, ISO-8859-1 and UTF-16LE input, frozen strings, and UTF-8, binary, US-ASCII, Shift_JIS and ISO-8859-1 targets. Fixed cases add `nil`, Symbols, Integers, String subclasses, `BasicObject` with and without `to_s`, `to_str` and `b`, and encoding arguments whose `to_str` changes its answer, raises on a second call or changes the input. This ran on Ruby 3.2, 3.3, 3.4 and 4.0, with and without `cgi/util` loaded, and with `cgi/escape`'s Ruby implementation. For these inputs, except `BasicObject`, the result's class, encoding, bytes, validity and frozenness, and every exception class and message, are the same. The optimized paths do not preserve arbitrary singleton overrides or redefinitions of core String methods: dispatch can be removed or added, and differs between native and Ruby CGI. The new tests cover the cases where the two libraries differ: the `*` and `~` mapping, the result encoding, String subclasses, the encoding argument and the invalid %-encoding message.

In Rails, cookies are read and written through these methods and form bodies are parsed by Rack, while query strings go through Rails' own parser. In whole requests of three open-source Rails apps, with these three methods from this branch loaded over Rack 3.2.7 (whose versions equal main's), this removes 0.9% to 5.4% of the instructions per request without YJIT and 2.9% to 10.1% with it, mostly from the session cookie, and about 60 to 140 objects. A JSON request with no query and no cookie written moves +0.01% without YJIT and +0.04% with it, within the spread of three unchanged runs. Each figure is against the mean of three unchanged runs; YJIT compiled and invalidated nothing in any measured window.
