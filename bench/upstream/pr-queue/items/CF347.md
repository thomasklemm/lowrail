# Remove Redis runtime dependency with Solid Cable

## Summary

Replace Action Cable's Redis adapter with Solid Cable, using a separate SQLite database at `storage/db/production_cable.sqlite3`. Together with the Solid Cache and Solid Queue changes, this removes Redis as a runtime dependency. Cable broadcasts are transient and are not migrated; active WebSockets reconnect after deployment.

- Uses the Solid Cable 4.1 series and the Rails default 100 ms poll interval / one-day retention as starting points, not as performance claims.
- Development uses Rails' default `async` adapter, since jobs run in the server process there; no development cable database is needed.
- `db:prepare` creates the Cable database from its checked-in schema. Production cache/queue/cable databases are isolated from primary storage; the performance environment is configured for all three adapters.
- Removes Redis service/configuration and runtime-only Redis/Kredis gems. Redis remains useful for the frozen historical benchmark baseline and upgrade guidance for older releases.
- The lockfile retains x86_64 and aarch64 Linux plus arm64/x86_64 Darwin platforms.

## Deployment and backup / restore

Every web and job process must use the same Solid Cable database; per-host SQLite files partition broadcasts and disconnects, and mixed Redis/Solid Cable processes cannot exchange broadcasts during a rolling cutover. Deploy on shared storage (or use a shared database service); otherwise retain Redis.

Queue, cache and Cable databases are disposable. Backups snapshot only the primary database online, as today; the archive command excludes the three disposable databases, and the restore hook deletes any left in the volume so `db:prepare` recreates them empty.
