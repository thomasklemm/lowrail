# Remove Redis runtime dependency with Solid Cable

Replace Action Cable's Redis adapter with Solid Cable, using a separate SQLite database at `storage/db/production_cable.sqlite3`. Together with the Solid Cache and Solid Queue changes, this removes Redis as a runtime dependency. Cable broadcasts are transient and are not migrated; active WebSockets reconnect after deployment.

Production uses a 100 ms poll interval and one-day retention. Development uses the `async` adapter, which only broadcasts within one server process. Startup creates the Cable database from its checked-in schema. Cache, queue and Cable storage stay separate from the primary database; the performance environment gets all three adapters. Redis services, configuration and runtime gems are removed; Redis remains only in the historical benchmark baseline and older upgrade guidance.

This includes #345 (Solid Cache) and #346 (Solid Queue), which should merge first. [Compare the changes after #346](https://github.com/thomasklemm/once-campfire/compare/feat/solid-queue-cutover...deps/solid-cable-removal); that comparison still includes the Solid Cache prerequisite, not just Cable.

Every web and job process must use the same Solid Cable database; per-host SQLite files partition broadcasts and disconnects, and mixed Redis/Solid Cable processes cannot exchange broadcasts during a rolling cutover. Deploy on shared storage (or use a shared database service); otherwise retain Redis.

Backups snapshot only the primary database. The archive excludes queue, cache and Cable databases, and restore recreates them empty. All pending jobs are lost, including unfinished deletion work.
