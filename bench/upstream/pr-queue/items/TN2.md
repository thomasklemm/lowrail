# Fix Time.new with a zone object that converts to a UTC offset or name

A zone argument that isn't a String or an Integer is tried as a timezone object first. When it has no `local_to_utc`, `time_init_vtm()` falls back to `utc_offset_arg()`, which converts it with `to_str`. That fallback handled only a nil result:

```ruby
o = Object.new
def o.to_str = "UTC"   # also "Z", "-00:00"
Time.new(2026, 1, 1, 0, 0, 0, o)  # [BUG] Segmentation fault
```

`utc_offset_arg()` returns `UTC_ZONE` (`Qundef`) for these, which was then used as an offset in `vtm_add_offset()`. `UTC_ZONE` came with 4f9ab3a01a (2.7.0), which converted it only in the String branch. It now takes the UTC path, as a String `"UTC"` does.

When `Time.find_timezone` resolves the converted name, `zone_timelocal()` set up the time, but since 337b4b6344 (2.6.0) the code went on and recomputed it from the system's local zone. It now returns there, so the result matches passing the name as a String.

An offset such as `"+25:00"` gave `+2500`, because `validate_vtm()` had already run; it now raises "utc_offset out of range" like the String.
