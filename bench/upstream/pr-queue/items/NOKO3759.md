# Call `children` once in `DocumentFragment#css`

**What problem is this PR intended to solve?**

`DocumentFragment#css` calls `children` twice when the fragment is not empty: once for `children.any?` and once to run the search. Each call builds a new NodeSet and passes it through the document's decorators, and the first one is thrown away. On a Loofah document, decorating the NodeSet extends it with `Loofah::ScrubBehavior::NodeSet`, which creates a singleton class and costs more than the NodeSet itself. Keeping the first NodeSet saves 1.5% of the instructions of a search on an HTML5 fragment and 5.5% on a Loofah one.

| `fragment.css("action-text-attachment")` | Before | After |
| --- | ---: | ---: |
| HTML5 fragment, Ruby 4.0 | 231.7k instructions, 41 objects | 228.2k, 39 objects |
| HTML5 fragment, YJIT | 208.9k instructions | 205.7k |
| Loofah HTML5 fragment, Ruby 4.0 | 327.3k instructions, 79 objects | 309.4k, 70 objects |
| Loofah HTML5 fragment, YJIT | 302.5k instructions | 286.1k |

Instructions are Callgrind counts per call with system libxml2. Action Text calls this when it renders rich text, and Discourse in its post processing: in six of the open-source Rails apps I profile, that is about one to nine calls per request on average. I found it in a census of gem allocations in those apps.

**Have you included adequate test coverage?**

The result is the same; only a decorator or `children` override with side effects would notice that it runs once instead of twice. Existing tests cover both branches: `css` on non-empty XML fragments, `at_css` on HTML5 fragments, and an empty HTML4 fragment.

**Does this change affect the behavior of either the C or the Java implementations?**

No. It is Ruby code that both use, and on JRuby `XmlNode#children` also builds and decorates a new NodeSet on every call.
