# Find SQLite tables by any ASCII case of their name in the schema readers

The batched SQLite schema readers require exact table names: `columns("widgets")` raises `StatementInvalid` for a table created as `Widgets`. Ransack 6.1.2 [disables this case pending a Rails fix](https://github.com/activerecord-hackery/ransack/blob/2700b29d2f2515f616c0e7e93d71671e7d9e84d2/spec/ransack/active_record/context_spec.rb#L93-L112). A temporary table shadowing a permanent one also produces duplicate columns and indexes and a composite primary key.

The first commit excludes permanent tables and views hidden by temporary ones. The second restores ASCII-case-insensitive lookups, including that hiding check. Names such as `Ärger` and `ärger` remain distinct.

Collations, auto-increment and check constraints now come from the resolved table's CREATE statement; 8-1-stable could miss this metadata or read it from the permanent table. Temporary and permanent indexes sharing a name remain a separate issue.

**P2 must-fix: a registered NOCASE collation is not SQLite identifier equivalence.** In `activerecord/lib/active_record/connection_adapters/sqlite3/schema_statements.rb:78`, the new exclusion can remove a permanent table that SQLite does not consider shadowed. Registering a Unicode-aware `NOCASE` is supported through sqlite3's public `Database#collation` API. It changes string comparisons, not identifier lookup. This connection-local API registration is not a global Ruby/core-method monkeypatch. #### Query counts, cost and upstream-readiness judgment

Notifications confirm `columns("Widgets")` takes one query for main `Widgets`, `columns("widgets")` takes two,
and `foreign_keys("widgets")` takes **three**. This is constant per batch, not N+1: **the third query on an
exceptional spelling is acceptable by itself**, provided the earlier at-most-two target is explicitly relaxed.
It is not acceptable to claim the target was met universally. Exact requested names are not sufficient either:
main `Widgets` hidden by temp `widgets` makes `columns("Widgets")` take two queries, despite that requested
name existing verbatim in main. Empty arrays still return `{}` from every reader.

**I disagree with Astra's performance/readability acceptance.** This is a correctness fix, so the L0-L3 speed-gain
bars do not apply. The separate rule to rule out a clear slowdown on a common path does apply. The builder's
+16% batched-trio and +43% scalar-column figures are material, not noise; +130 microseconds is a per-reader
diagnostic, not measured request latency. Schema reads are cold/cached, but migrations, schema-cache population,
model initialization and schema dumps still pay them. The ordinary exact-name path should not acquire this much
additional work solely to restore the exceptional spelling behavior.

#### Maintainability, cold read and guards

**L2, not acceptable as currently combined with the common-path regression.** The +240/-53 total is not itself
the problem: +178/-22 is tests, and the adapter was already 1,003 lines before growing to 1,033. No new 1k-line
threshold crossing, no need to extract an arbitrary adapter module. The problem is `table_structures` growing
from one grouped pragma query into two mixed catalog/column result formats, NULL sentinel rows, two differently
keyed intermediate maps, and a lambda whose result changes when its captured `permanent` local is rebound.
The phase boundary also explains the three correctness failures: introspection precedes authoritative identity.

Cold read: read exact catalog matches and every temporary identity; partition catalog sentinels from columns;
prefer a temporary ASCII identity; if its stored spelling has no columns, read unresolved names again and every
permanent identity; rebind the permanent map; insert fallback rows under their eventual stored spelling; then
emit the original requested keys plus a hidden third tuple member for FK schema identity. That is too much state
to justify as a small local lookup repair. Named helpers that merely split those phases would not remove it.

```text
Run the temporary index shadowing test only where SQLite allows it

SQLite refuses to create a temporary index named like a permanent table
before 3.38 ("there is already a table named shadowed"), so the schema
reader test that set one up errored on 3.37 before asserting anything.
Give that case its own test, defined on 3.38 and later, and keep the
temporary table and trigger cases on every supported version.

Find SQLite tables by any ASCII case of their name in the schema readers

The batched schema readers filtered sqlite_master and sqlite_temp_master
with an exact IN match and keyed the rows by the stored name, while
SQLite matches table names without regard to ASCII case. A model whose
table_name differs in case from the CREATE TABLE statement could no
longer read its columns, primary key or indexes.

Resolve each name the way SQLite does, temporary tables and views first
and ignoring ASCII case only, and key the rows by the name that was
asked for. Indexes come from the unqualified pragma_index_list, kept
only when the temporary or main schema has an index list for the name,
so attached databases stay out and no view is expanded. Table structures
still start from the catalog rows stored under the exact name and bring
every temporary table and view along: one whose name differs only in
ASCII case hides the permanent table, and its columns and CREATE
statement are the ones read. A name that resolves to no row read this
way, because it is not stored as asked or such a temporary table hides
it, is read once more in the schema it resolved to, temporary or else
main, together with every permanent name. Any other name costs one
query as before. Foreign keys are read from the table each name resolved
to.

Names are compared with downcase(:ascii), which folds them as SQLite
does. COLLATE NOCASE, lower() or LIKE would not do: an application can
redefine them, and LIKE treats % and _ as wildcards. pragma_table_list
resolves names too, but it needs SQLite 3.37 and Rails supports 3.35.

The check the previous commit added to the shared CTE moves into the
table structures query, so the CTE is as before.
```
