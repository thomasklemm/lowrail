# Find SQLite tables by any ASCII case of their name in the schema readers

2cb3daba96 batched the SQLite schema readers, which now match table names exactly. The previous pragma-based readers matched them the way SQLite does, ignoring ASCII case. So a model whose `table_name` is `"widgets"` can no longer read a table created as `Widgets`: `columns` and `primary_key` raise `StatementInvalid`, and indexes and foreign keys come back empty. ransack's [`context_spec.rb`](https://github.com/activerecord-hackery/ransack/blob/fbc3baf164da2a80435d5678a77924c66472f694/spec/ransack/active_record/context_spec.rb#L73-L81) hits this.

The readers now match with `COLLATE NOCASE`, which folds only ASCII, like SQLite identifiers, so `Ärger` and `ärger` stay two tables. A table read with a different ASCII-case spelling also gets its collations and auto-increment, which 8-1-stable lost.

The batched readers join each pragma to a list of `sqlite_master` and `sqlite_temp_master` rows. When a temporary table has the same name as a permanent one, both rows match, and the pragmas resolve both to the temporary table, as SQLite does. So columns and indexes are duplicated, and the primary key becomes composite. The first commit makes the list take a permanent table or view only when no temporary table or view has its name, which is how SQLite resolves names; the second makes that check case-insensitive too. Collations and check constraints now come from the temporary table's CREATE statement; 8-1-stable read the columns from the temporary table but the statement of the permanent one.

Shared index names remain a separate issue.
