# Find SQLite tables by any ASCII case of their name in the schema readers

The batched SQLite schema readers require exact table names: `columns("widgets")` raises `StatementInvalid` for a table created as `Widgets`. Ransack 6.1.2 [disables this case pending a Rails fix](https://github.com/activerecord-hackery/ransack/blob/2700b29d2f2515f616c0e7e93d71671e7d9e84d2/spec/ransack/active_record/context_spec.rb#L93-L112). A temporary table shadowing a permanent one also produces duplicate columns and indexes and a composite primary key.

The first commit excludes permanent tables and views hidden by temporary ones. The second restores ASCII-case-insensitive lookups with `COLLATE NOCASE`, including that hiding check. Names such as `Ärger` and `ärger` remain distinct.

Collations, auto-increment and check constraints now come from the resolved table's CREATE statement; 8-1-stable could miss this metadata or read it from the permanent table. Temporary and permanent indexes sharing a name remain a separate issue.

**P2 must-fix: a registered NOCASE collation is not SQLite identifier equivalence.** In `activerecord/lib/active_record/connection_adapters/sqlite3/schema_statements.rb:78`, the new exclusion can remove a permanent table that SQLite does not consider shadowed. Registering a Unicode-aware `NOCASE` is supported through sqlite3's public `Database#collation` API. It changes string comparisons, not identifier lookup. This connection-local API registration is not a global Ruby/core-method monkeypatch. The three new lookup predicates also depend on the application collation, while `group_by_table` uses Ruby's fixed ASCII folding; the two notions of equality can disagree.

Reproduction, using each checkout's Active Record/Active Support/Active Model on the load path:

```ruby
require "active_record"
ActiveRecord::Base.establish_connection(adapter: "sqlite3", database: ":memory:")
c = ActiveRecord::Base.lease_connection
comparator = Object.new
def comparator.compare(a, b)
  a.downcase <=> b.downcase
end
c.raw_connection.collation("NOCASE", comparator)
c.execute 'CREATE TABLE "Ärger" (upper integer)'
c.execute 'CREATE TEMP TABLE "ärger" (lower integer)'
p c.exec_query("SELECT name FROM pragma_table_xinfo('Ärger')").rows
p c.columns("Ärger").map(&:name)
```

The pragma returns `[["upper"]]` everywhere. Pinned main and 8-1-stable return `["upper"]` from `columns`; head raises `ActiveRecord::StatementInvalid: Could not find table 'Ärger'`. This also makes `primary_keys` fail and silently loses the excluded table's index/foreign-key/check rows. The failure is in the added predicate, not the rebase: range-diff marks both rebased commits identical. The same catalog predicate independently excludes the table in Python's SQLite 3.46.1; the Rails repro uses sqlite3 2.10.2 / SQLite 3.54.1. SQLite explicitly permits replacing collations: [create_collation](https://www.sqlite.org/c3ref/create_collation.html); its [datatype documentation](https://www.sqlite.org/datatype3.html#collation) describes ASCII folding as the built-in NOCASE behavior, not an invariant of every registered comparator.

**Smallest safe correction in scope:** keep the reader/building code, but resolve table/view names in one shared catalog-selection step using `downcase(:ascii)`, prefer temporary rows for each canonical name, and retain each selected row's schema and stored spelling for the batched pragma/CREATE lookup. Do not use the application's `NOCASE` to decide identity or hiding. Keep index-name resolution separate, rather than enlarging this into the existing shared-index bug. Add the reproduction above as a public-reader regression on a disposable connection. Merely changing the hiding predicate to `LIKE` is wrong for wildcard names and `case_sensitive_like`; substituting SQL `lower` is not a general solution either, since extensions can give it Unicode folding. This is a proposed correction, not an implementation or a verified patch. After removing the NOCASE dependency, replace the body's mechanism sentence exactly with: “The second restores ASCII-case-insensitive lookups, including that hiding check.” A body-only edit does not repair the existing exact-name lookup regression.
